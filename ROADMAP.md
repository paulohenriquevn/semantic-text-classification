# TalkEx — Real-Time Attendance Monitoring — Roadmap

> Generated by `/roadmap-init` on 2026-07-29 from slug `realtime-attendance-monitoring`.
> This is a **macro** roadmap. Decomposition into tasks is the job of `/to-plan` per milestone.

## Vision

TalkEx becomes the real-time conversation-intelligence platform — the "fleet platform" that
Macaw Voice (`../jvscribe`) explicitly leaves out of scope — turning 100% of on-device PT-BR
transcriptions into **live, evidence-backed monitoring** for call-center supervisors and QA.
Cheap cascade filters (rules/lexical) fire first; ML sentiment and hybrid search layer on top;
everything lives in a 30-day hot window on a single Postgres/TimescaleDB spine (ADR-005), with
anonymized samples exported for retraining before purge. The bet: because Macaw makes every call
visible at ~$0 marginal cost, the missing piece is turning that firehose into action *while the
call is still live*, not in a report next week.

## Problem

**Root problem:** Call-center operations have near-zero real-time visibility into the *content*
and *emotional trajectory* of live conversations. QA audits 1–2% of calls retrospectively, days
later; critical signals (cancellation intent, escalation, compliance breach, customer rage) are
detected only after the customer already churned or the regulatory failure already happened. With
Macaw producing on-device transcripts of 100% of calls at ~$0 marginal cost, the missing piece is
a platform that turns that firehose into actionable real-time monitoring.

**Whose pain:** Supervisors/QA (blind to what happens live; tiny, late sample) · the business
(avoidable churn + compliance risk seen only in the rear-view mirror) · agents (no live coaching;
errors corrected far too late).

## Users

- **Primary:** Supervisor de operação (operations supervisor, internal, one ops team per pilot) —
  monitors N live agents, receives prioritized alerts, drills into the live conversation. The
  screen that stays open all day; if the supervisor does not use it, the product failed.
- **Secondary:** QA analyst (100% coverage via hybrid search + rules, audits/labels, consumes the
  near-real-time / 30-day history) and Operations manager/head (aggregated dashboards only —
  sentiment trends, cancellation rate per queue/domain, script adherence).

## Scope

### In scope (V1 — required to call this project alive)

- Streaming ingestion of Macaw transcripts (multi-stream fan-in) → segmentation into turns/windows
  (reuses existing TalkEx segmentation + context-window builder).
- ADR-005 storage operational: Postgres/TimescaleDB (30-day hot window) + pgvector + BM25, with
  native retention/purge and compression.
- Online cascade classification: rules/lexical (existing DSL engine) firing instantly + ML
  sentiment per turn/window, CPU-first.
- Real-time alerting with evidence when a critical rule fires (cancellation, escalation, negative
  sentiment drop), pushed live to the supervisor.
- Supervisor live-monitoring screen (active calls + state + drill-down with highlighted evidence)
  and an aggregated minimal dashboard (continuous aggregates).
- Hybrid BM25 + semantic search over the 30-day window for QA.

### Explicitly out of scope

- ASR / transcription — *why excluded:* it is Macaw's job (separate repo); the platform consumes
  transcripts, it does not produce them.
- Live agent-facing coaching (whisper/suggestions on the agent's own screen) — *why excluded:*
  changes the product into an agent tool and adds UI/latency surface; post-V1.
- Dialer / PABX-CTI integration / barge-in — *why excluded:* telephony, not NLP; integrates with
  the dialer, not TalkEx.
- Heavy offline ML (unsupervised intent discovery, topic clustering, LLM summarization, predictive
  quality score) — *why excluded:* that is the KB_Complementar offline pipeline; post-V1.
- LLM in the online path — *why excluded:* the axiom is "LLMs offline only"; cost/latency forbid it
  in the real-time V1.
- LGPD/compliance as a product (consent management, per-client configurable retention, fine-grained
  RBAC, multi-tenant) — *why excluded:* V1 assumes one tenant + the fixed 30-day retention of ADR-005.
- Mobile app / external alert channels (push/Slack/email) — *why excluded:* V1 is web, supervisor at
  the desk.
- Training a bespoke sentiment model from scratch — *why excluded:* V1 uses a pre-trained PT-BR model;
  from-scratch training is post-V1 / dissertation work.

> Items in this list are off-limits for V1. To reconsider, write a new roadmap revision — do not
> silently expand scope.

## Constraints

| Category | Constraint |
|---|---|
| Stack | Python + FastAPI (already in the project); ADR-005 DB (Postgres + TimescaleDB + pgvector + BM25 via pg_search/tsvector — no ClickHouse/Qdrant in V1); frontend React + Vite + TypeScript + Tailwind (reuse the existing demo). |
| Compliance / legal | LGPD as an architecture posture (30-day retention + native purge + anonymization of the retraining sample), NOT a product feature in V1. |
| Deadline | None fixed — evidence-driven milestones ("architecture is measured, not chosen by conviction"). |
| Team | Small team; discipline of measure-before-scaling and always compare against the BM25 baseline. |
| Runtime target | Hybrid retrieval p95 < 200 ms; alert turn-arrival→screen p95 < ~2 s `[TO VALIDATE]`; sustained ingest ~150–300 turns/s. CPU-first (coherent with Macaw); GPU not a premise. |
| Budget (infra, tooling) | Marginal compute favored (single-node Postgres/Timescale over multi-service); no premise of paid vector-DB or OLAP service in V1. |

## Success criteria

**V1 ship criterion (measurable):** In a real pilot (one queue/domain, dozens of live agents), ALL
hold: (1) 100% of active calls appear on the supervisor screen in real time; (2) critical-turn →
on-screen alert latency p95 < ~2 s `[TO VALIDATE]`; (3) hybrid-retrieval p95 < 200 ms under
concurrent ingest; (4) sentiment macro-F1 ≥ ~0.70 on the labeled PT-BR set, **beating the
BM25/lexical baseline** (aligned with the existing experiments' H2 ≈ 0.72); (5) critical-alert
precision (cancellation/escalation) ≥ 0.8 with no false-positive flooding; (6) purge working — raw
data > 30 days auto-dropped, anonymized retraining sample exported before the drop.

**North-star metric (tracked post-launch):** rate of "alert-triggered interventions that changed
the call outcome" — % of at-risk calls where a real-time alert led to an action and the outcome
improved (retention, de-escalation, compliance fixed on the spot); in one line, "conversations
saved per unit of time". Resists gaming (not alert count, not model accuracy — outcome impact).
Initial proxy while outcome is not end-to-end instrumentable: supervisor alert-engagement rate
(alerts acted on with evidence).

## Milestones

> Each milestone has a checkbox in its header. Flip `[ ]` → `[x]` as you complete it. Status lives
> in this document; no external tracker required.

### M0 — [x] Walking skeleton

**Objective:** End-to-end thinnest slice — ingest one live transcript stream, segment into
turns/windows, run one cascade check (a rule + sentiment stub), persist to Postgres/Timescale, and
surface one live alert on a minimal supervisor screen.

**Definition of done (all must hold):**

- [ ] A transcript segment posted to a streaming endpoint lands as a Turn in a Timescale hypertable with timestamp.
- [ ] The existing segmentation + context-window builder produces a window from the live stream.
- [ ] One DSL rule fires on a window and produces an alert row carrying evidence.
- [ ] A minimal supervisor web page shows the active conversation and the alert live within a few seconds.

**Dependencies:** none (this is the foundation).

**Top risks:**

1. The ingest contract with Macaw (transcript segment schema, partial vs final) is undefined — must be pinned first.
2. Postgres/Timescale/pgvector local setup friction slows the skeleton.

---

### M1 — [x] Ingestion & storage foundation (ADR-005)

**Objective:** Productionize the ADR-005 storage spine — Timescale hypertables + pgvector + BM25
with 30-day retention/compression and multi-stream fan-in ingestion.

**Definition of done:**

- [ ] Schema for conversation/turn/window/features as hypertables; migrations reproducible from scratch.
- [ ] Retention policy drops raw chunks at 30 days; compression on chunks older than N days verified.
- [ ] Multi-stream ingest sustains a synthetic target (~300 turns/s) without loss; backpressure handled.
- [ ] pgvector + BM25 (pg_search or tsvector fallback) indexes built and queryable; extension coexistence verified.

**Dependencies:** M0.

**Top risks:**

1. Extension coexistence (pg_search + TimescaleDB + pgvector) is unverified — may force the tsvector fallback.
2. Streaming ingest contends with concurrent queries on one instance — may force ingest/replica split.

---

### M2 — [x] Online sentiment & feature extraction (ML)

**Objective:** Add online sentiment + core features per turn/window via a lightweight PT-BR model in
the cascade, CPU-first, benchmarked against the BM25/lexical baseline.

**Definition of done:**

- [ ] Sentiment classifier emits label + score + evidence per window at online CPU latency, fed by the cascade.
- [ ] Sentiment macro-F1 ≥ ~0.70 on the labeled PT-BR set, beating the BM25/lexical baseline.
- [ ] Features (sentiment, intent scores, speaker, channel) persisted as wide feature columns (ADR-005 "Leitura A") in the hypertable.
- [ ] p95 online classification latency measured and within the per-turn budget at target ingest rate.

**Dependencies:** M1.

**Top risks:**

1. CPU embedding throughput at ~300 turns/s may not fit budget — the cascade must keep ANN/embedding off the hot path for most turns.
2. PT-BR sentiment dataset scarcity/quality caps achievable macro-F1.

---

### M3 — [x] Real-time rule engine & alerting

**Objective:** Real-time critical-event alerting — the DSL rule engine evaluates each incoming window
and emits prioritized, evidence-backed alerts pushed live to the supervisor.

**Definition of done:**

- [ ] Rule engine evaluates windows online; critical rules (cancellation, escalation, negative-sentiment drop) fire with evidence.
- [ ] Alerts reach the supervisor UI in p95 < ~2 s from turn arrival.
- [ ] Critical-alert precision ≥ 0.8 on a validation set (no false-positive flooding).
- [ ] Every alert carries full evidence (label, score, threshold, model version, text evidence).

**Dependencies:** M2.

**Top risks:**

1. Alert precision vs recall tradeoff — too-loose thresholds flood the supervisor; too-tight miss real risk.
2. Live-push mechanism (LISTEN/NOTIFY) has scaling limits — may need a CDC/queue as the fleet grows.

---

### M4 — [x] Supervisor live-monitoring UI

**Objective:** Ship the anchor product surface — active-call list with real-time state, drill-down
into the conversation with highlighted evidence, and a prioritized alert inbox.

**Definition of done:**

- [ ] Supervisor sees all active calls with live sentiment/flag state.
- [ ] Drill-down shows the live conversation with highlighted matched fragments and per-predicate evidence.
- [ ] Alert inbox is prioritized and actionable (acknowledge, open call).
- [ ] Reuses and extends the existing React + Vite + TypeScript + Tailwind demo frontend.

**Dependencies:** M3.

**Top risks:**

1. Real-time UI update volume (many concurrent calls) strains the client — needs windowing/virtualization.
2. Alert fatigue / cognitive load — the UI must prioritize ruthlessly or the supervisor tunes it out.

---

### M5 — [ ] Hybrid search & QA over 30 days

**Objective:** Give QA 100% coverage — hybrid BM25 + semantic search over the 30-day window with
metadata filters, plus an audit/label workflow.

**Definition of done:**

- [ ] Hybrid retrieval (BM25 + ANN + fusion) over the 30-day window with p95 < 200 ms under concurrent ingest.
- [ ] QA can search by criterion (compliance, script, sentiment, intent) and open matched windows with evidence.
- [ ] Audit/label action persists labels destined for retraining.

**Dependencies:** M1, M2.

**Top risks:**

1. p95 under concurrent write/query load may miss target — the ADR-005 pilot must confirm before committing.
2. Hybrid fusion relevance quality — must be benchmarked against the BM25-only baseline.

---

### M6 — [ ] Aggregated dashboards (continuous aggregates)

**Objective:** Manager dashboards from Timescale continuous aggregates — sentiment trends,
cancellation and alert rate per queue/domain, script adherence.

**Definition of done:**

- [ ] Continuous aggregates compute rollups incrementally (e.g., cancellation-intent rate per queue per 5 min) with no full scan.
- [ ] Dashboard renders trends with acceptable freshness/latency.
- [ ] Rollups retained beyond 30 days (long-term business memory) while raw data purges.

**Dependencies:** M1, M2.

**Top risks:**

1. Continuous-aggregate refresh latency vs "real-time" expectation — set honest freshness SLOs.
2. Defining KPIs that are meaningful to the operation rather than vanity metrics.

---

### M7 — [ ] Retraining loop & data lifecycle

**Objective:** Close the offline data lifecycle — export anonymized retraining samples to object
storage before purge, and retrain the sentiment/intent models on accumulated labels.

**Definition of done:**

- [ ] Anonymized/pseudonymized retraining sample exported to Parquet/object storage before the 30-day chunk drop.
- [ ] Retraining pipeline consumes QA labels + exported samples and produces a new model version, benchmarked vs the deployed one.
- [ ] Model versioning tracked; every prediction records its model version (existing evidence axiom).

**Dependencies:** M1, M2, M5.

**Top risks:**

1. Anonymization correctness is an LGPD-critical failure mode — a leak of raw PII into the cold sample is unacceptable.
2. Label volume/quality may be insufficient to show retraining gains over the pre-trained baseline.

---

### M8 — [ ] Pilot hardening & V1 ship

**Objective:** Run the production pilot on one queue/domain and prove every V1 ship criterion under
real load; harden for operation.

**Definition of done:**

- [ ] All V1 ship criteria pass in the pilot: 100% coverage, alert p95 < ~2 s, retrieval p95 < 200 ms, sentiment macro-F1 ≥ 0.70 > baseline, critical-alert precision ≥ 0.8, purge working.
- [ ] Supervisor acts on ≥ N alerts/day with evidence (north-star proxy: alert-engagement rate tracked).
- [ ] Operational runbook, health/latency monitoring of the monitor itself, and failure recovery in place.

**Dependencies:** M0, M1, M2, M3, M4, M5, M6, M7.

**Top risks:**

1. Real-world data drift vs synthetic pilots — numbers proven on synthetic load may degrade on live 8 kHz call-center speech.
2. Operational buy-in — the supervisor must trust the alerts enough to change behavior (the north-star depends on it).
